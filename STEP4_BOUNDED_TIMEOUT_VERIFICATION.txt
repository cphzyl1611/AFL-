================================================================================
DEFENSIVE PROPERTIES
================================================================================

1. Fail-Closed:
   - Timeout returns score=0.0, ok=0
   - Invalid flag propagates to caller
   - Input rejected before target execution
   - No false validity grant on scorer failure

2. Campaign Resilience:
   - Single RPC timeout does NOT block entire campaign
   - Fuzzing loop continues with next mutation
   - No indefinite hang (R39 root cause eliminated)

3. Timeout Duration Justification:
   - Python reference: 1 second (nv_body_valid.py line 245)
   - C implementation: 2 seconds (more defensive)
   - Canonical SE model inference: ~20-50ms (measured in R38C)
   - 2 seconds allows 40-100× normal latency
   - Sufficient for model inference + Unix socket overhead
   - Not so long that a hung scorer stalls campaign throughput

4. Error Path Coverage:
   - connect() failure → return 0.0 (line 845-848)
   - send() failure → return 0.0 (line 926)
   - recv() timeout → return 0.0 (line 955)
   - parse failure → return 0.0 (line 973)
   - All paths close(fd) before return
   - All paths return ok=0 on failure

================================================================================
COMPARISON WITH R39 FAILURE MODE
================================================================================

R39 (No Timeout):
  - Protocol V1 sent to Protocol V2 scorer
  - Scorer raises JSONDecodeError, prints to subprocess.PIPE
  - Scorer exception handler catches, continues loop WITHOUT sending response
  - AFL++ recv() blocks indefinitely (no timeout)
  - After 90 seconds: timeout command kills process tree
  - Campaign result: ARTIFACT_CONTRACT_FAILED, exit code 124

Post-Repair (With Timeout):
  - Protocol V2 sent to Protocol V2 scorer (alignment fixed)
  - If scorer fails for ANY reason and does not send response:
    - recv() returns after 2 seconds with EAGAIN/EWOULDBLOCK
    - RPC classified as failure (NV_V_REJ_RPC_FAIL)
    - Input rejected, fuzzing continues with next mutation
  - Campaign continues running until:
    - max_test_cases reached, OR
    - user interrupts (Ctrl+C), OR
    - scheduler exhaustion

INDEFINITE_BLOCKING_ELIMINATED = YES

================================================================================
OBSERVABILITY
================================================================================

Timeout Detection in Logs:
  - fuzzer_stats will show nv_invalid_rpc_fail_cnt > 0
  - High nv_invalid_rpc_fail_cnt indicates:
    - Scorer subprocess died or hung
    - Network partition (unlikely for Unix socket)
    - Scorer processing extremely slow (>2 seconds per request)

Diagnostic Path (if timeouts occur in production):
  1. Check scorer_trace.jsonl for recent entries
  2. Check scorer stdout/stderr for exceptions (Step 5)
  3. Check scorer process is alive (ps aux | grep nv_valid_server)
  4. Check Unix socket exists (ls -la $NV_VALID_SOCK)
  5. If scorer alive but not responding → likely infinite loop or deadlock
