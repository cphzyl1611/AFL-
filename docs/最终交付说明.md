## 2. 当前项目定位

当前项目已经形成一套面向 JSON API 平台的 AFL++/harness 组合式模糊测试与有效性验证框架，具备以下能力：

- 支持通过 `targets/*.json` 描述目标平台 HTTP/REST JSON 接口
- 支持通过 `validity/*.json` 配置 body-level 输入有效性规则
- 支持 `nv_http_harness.py` body-only fuzz 与 harness 级有效性统计
- 支持 AE score 服务接入与 `integration/decision_engine.py` 二阶段判定
- 支持 O2OA 主线：AE@1.0 默认，GAN online 作为二阶段增强
- 支持 Flowable 支线：Flowable-AE v2@6.3 + `flowable_rule_v1` 最小二阶段验证，`is_mainline=false`
- 支持 `runner/fuzz_test_runner.py` 与 `integration/fuzz_adapter.py` 提供 runner/adapter 级 `submit/query/stop/report_query` 任务语义

当前在 O2OA 平台上已完成阶段验收主线验证；Flowable 作为第二平台最小校准验证支线。当前动态异构冗余仅指模糊测试有效性验证链路中的二阶段判定机制，不表述为完整拟态系统级执行体调度、自愈或重构机制。

## 11. `src_core/` 目录说明

如果你最终决定把核心 Python 文件单独整理到这里，则建议如下：

### 11.1 `nv_http_harness.py`

通用执行器。

负责：

* 读取 body-only 输入
* 加载 target 配置
* 调用 body validator
* 注入鉴权
* 发真实 HTTP 请求
* 写状态统计

### 11.2 `nv_body_valid.py`

通用 body-level 有效性验证器。

负责：

* JSON 规范化
* 全局规则检查
* endpoint 规则检查
* score RPC 调用
* 返回标准验证结果

### 11.3 `nv_valid_server_mock.py`

mock score 服务。

作为当前 score 后端占位实现，未来可替换为真实 SE-fAnoGAN-ES 服务。

> 如果你暂时不移动这 3 个文件，也没关系，但应在 README 或本说明中明确它们是核心模块。

## 14. 当前正式结论说明

当前阶段建议正式采用如下口径：

### 14.1 主实验

当前已完成基于通用脚本的多接口 baseline / rule_only 主实验。

一级规则验证已可作为当前阶段正式有效性验证方案。

### 14.2 增强实验

二级 score 已成功接入并具备初步筛选能力，但自动 fuzz 条件下的增益仍不稳定，因此当前更适合作为增强模块。

### 14.3 框架能力

当前系统已具备：

* 平台无关 target 配置能力
* 规则可配置能力
* 通用执行能力
* score 可插拔能力

## 15. 推荐的使用顺序

### 场景 A：复现 O2OA 本地实验

1. 先看 `README_O2OA_Local.md`
2. 配置 O2OA 本地环境
3. 使用 `targets/o2oa_query.json`
4. 运行 `run_main_baseline_rule_generic.sh`

### 场景 B：接入新平台

1. 先看 `README.md`
2. 再看 `docs/new_platform_migration_guide.md`
3. 新建 `targets/new_platform.json`
4. 新建 `validity/new_platform_rules.json`
5. 准备新种子目录
6. 先手工单次验证
7. 再跑 baseline / rule_only
