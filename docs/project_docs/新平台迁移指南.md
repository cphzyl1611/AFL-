# 新平台接入最小迁移指南

## 1. 文档目的

本文档用于指导使用者将当前“面向 JSON API 平台的 body-only 模糊测试与有效性验证框架”迁移到一个新的业务平台。  
目标不是重写项目，而是在尽量不改动主逻辑代码的前提下，只通过修改配置、规则和种子，完成新平台接入。

本指南特别适用于以下场景：

- 已有一个正在运行的 HTTP JSON API 平台
- 已获得测试账号、Token 或其他鉴权信息
- 需要快速接入当前模糊测试框架
- 希望后续还能继续使用一级规则验证和二级 score 验证

---

## 2. 迁移原则

新平台接入时，优先修改以下内容：

1. `targets/new_platform.json`
2. `validity/new_platform_rules.json`
3. `in/new_platform_body/`
4. 鉴权环境变量（如 `NV_TOKEN`）

尽量不要修改以下主逻辑文件：

- `nv_http_harness.py`
- `nv_body_valid.py`

如果必须修改主逻辑，优先检查是否能通过：
- target 配置
- validity 规则
- seed 模板
来解决问题。

## 4. 接入前准备清单

在开始迁移前，先确认你已经掌握以下信息：

### 4.1 平台基本信息
- 平台基础地址（Base URL）
- 是否可从当前环境访问
- 是否存在可用于健康检查的简单接口或页面

### 4.2 鉴权信息
- 是否需要 Token
- Token 放在 Header 还是 Cookie
- Header 名称是什么
- 是否使用 Bearer 前缀

### 4.3 接口信息
至少选择 1~3 个代表性的 JSON API 接口，明确：
- 接口名称（你自己定义的逻辑名称）
- 请求方法（GET / POST / PUT / DELETE）
- 请求路径（path）
- 正常 body 结构
- 必填字段
- 字段类型

### 4.4 可用样本
至少准备：
- 1 个合法请求样本
- 最好再准备 2~3 个边界样本

## 5. 第一步：创建目标平台配置文件

新建文件：

```text
targets/new_platform.json
```

这是“目标平台配置文件”，负责描述：

- 平台地址
- 健康检查地址
- 鉴权方式
- endpoint 列表
- body-only 模式
- 默认 body 模板

---

## 6. `targets/new_platform.json` 标准模板

下面是一份推荐模板：

```json
{
  "base": "http://example-api.local",
  "health": "/health",
  "auth": {
    "type": "bearer",
    "header": "Authorization",
    "token_env": "NV_TOKEN",
    "prefix": "Bearer "
  },
  "body_only_mode": 1,
  "default_endpoint": "query_items",
  "endpoints": [
    {
      "name": "query_items",
      "method": "POST",
      "path": "/api/items/query"
    }
  ],
  "body_templates": {
    "query_items": {
      "page": 1,
      "size": 10,
      "keyword": ""
    }
  }
}
```

---

## 7. `targets` 配置字段详细说明

### 7.1 `base`
平台基础地址。

示例：

```json
"base": "http://example-api.local"
```

最终请求 URL 为：

```text
base + path
```

例如：

```text
http://example-api.local + /api/items/query
= http://example-api.local/api/items/query
```

---

### 7.2 `health`
平台健康检查路径。

用于：
- 异常后恢复检测
- 快速确认平台是否在线

示例：

```json
"health": "/health"
```

如果平台没有专门健康检查接口，也可以选一个简单稳定、不会改库的 GET 页面。

---

### 7.3 `auth`
鉴权配置。

#### `type`
支持的常见类型：

- `none`：无鉴权
- `bearer`：Bearer Token
- `raw_token`：原始 token 写入 Header
- `cookie`：如果你后续扩展，也可支持 Cookie-only 模式

#### `header`
请求头字段名，例如：

```json
"header": "Authorization"
```

#### `token_env`
从哪个环境变量读取 token，例如：

```json
"token_env": "NV_TOKEN"
```

#### `prefix`
仅在 `bearer` 模式常用，例如：

```json
"prefix": "Bearer "
```

#### `also_cookie`
仅在 `raw_token` 场景常用。表示除了写 Header，还把 token 写进 Cookie。

例如：

```json
"also_cookie": "x-token"
```

---

### 7.4 `body_only_mode`
是否启用 body-only 模式。

当前推荐统一设为：

```json
"body_only_mode": 1
```

含义是：
- AFL 变异的输入只包含 JSON body
- 方法、路径、鉴权由 target 配置决定

这是当前框架最稳定、最适合 API 平台的模式。

---

### 7.5 `default_endpoint`
默认 endpoint 名称。

当启用 body-only 模式，但没有显式设置 `NV_ENDPOINT_NAME` 时，使用这个 endpoint。

示例：

```json
"default_endpoint": "query_items"
```

---

### 7.6 `endpoints`
接口列表。

每个 endpoint 推荐包含：

- `name`
- `method`
- `path`

例如：

```json
{
  "name": "query_items",
  "method": "POST",
  "path": "/api/items/query"
}
```

#### `name`
逻辑名称，后续会用于：
- `NV_ENDPOINT_NAME`
- `validity/new_platform_rules.json`
- body 模板索引

#### `method`
HTTP 请求方法。

#### `path`
请求路径，不包含 base。

---

### 7.7 `body_templates`
每个 endpoint 的默认 body 模板。

它主要用于：
- 生成初始种子
- 说明这个接口的典型 body 结构
- body-only 模式下提供“合理初值”

示例：

```json
"body_templates": {
  "query_items": {
    "page": 1,
    "size": 10,
    "keyword": ""
  }
}
```

---

## 8. 第二步：创建有效性规则文件

新建文件：

```text
validity/new_platform_rules.json
```

这个文件描述：
- 全局 JSON 限制
- endpoint 级规则
- required 字段
- 是否允许未知字段
- 字段级类型与长度/数量约束

---

## 9. `validity/new_platform_rules.json` 标准模板

```json
{
  "common": {
    "max_bytes": 8192,
    "max_depth": 6,
    "max_keys": 64,
    "max_string": 1024
  },
  "endpoints": {
    "query_items": {
      "type": "object",
      "required": ["page", "size", "keyword"],
      "allow_unknown": true,
      "properties": {
        "page": {
          "type": "integer"
        },
        "size": {
          "type": "integer"
        },
        "keyword": {
          "type": "string",
          "maxLength": 128
        }
      }
    }
  }
}
```

---

## 10. `validity` 规则字段详细说明

### 10.1 `common`
全局规则，对所有 endpoint 生效。

#### `max_bytes`
JSON body 最大字节数。

超过后直接 reject。

#### `max_depth`
JSON 最大嵌套深度。

超过后直接 reject。

#### `max_keys`
JSON 中允许的最大 key 总数。

超过后直接 reject。

#### `max_string`
任意字符串允许的最大长度。

超过后直接 reject。

---

### 10.2 `endpoints.<name>`
按 endpoint 名称定义规则。  
endpoint 名称必须与 `targets/new_platform.json` 中的 `endpoints[].name` 一致。

---

### 10.3 `type`
body 顶层类型。

当前推荐支持：
- `object`
- `array`

大部分业务接口都用 `object`。

---

### 10.4 `required`
必填字段列表。

只对顶层 `object` 有意义。

如果缺失任一字段，则 reject。

---

### 10.5 `allow_unknown`
是否允许出现 `properties` 未声明的字段。

- `true`：允许
- `false`：不允许，出现未知字段则 reject

建议在新平台接入初期先设置为 `true`，等规则成熟后再收紧。

---

### 10.6 `properties`
字段级规则。

当前框架建议先只使用：

- `type`
- `maxLength`
- `maxItems`

不要一开始就上太复杂的 schema。

---

### 10.7 `type`
字段类型，可用值建议包括：

- `string`
- `array`
- `integer`
- `number`
- `boolean`
- `object`
- `null`

---

### 10.8 `maxLength`
字符串最大长度，仅对字符串字段有效。

---

### 10.9 `maxItems`
数组最大元素个数，仅对数组字段有效。

---

## 11. 第三步：准备种子目录

新建种子目录：

```bash
mkdir -p in/new_platform_body
```

至少放 1 个合法 JSON 种子。

示例：

```bash
cat > in/new_platform_body/seed_query_items_0.json <<'EOF'
{"page":1,"size":10,"keyword":""}
EOF
```

如果要做二级 score 增强实验，可以额外准备：

```text
in/new_platform_body_score/
```

里面放：
- 正常样本
- 边界样本
- 合法但更异常的样本

---

## 12. 第四步：设置环境变量

进入项目目录：

```bash
cd ~/AFLplusplus
```

设置 target 文件：

```bash
export NV_TARGET_CONFIG=$PWD/targets/new_platform.json
```

设置 token：

```bash
export NV_TOKEN='你的真实token'
```

设置当前 endpoint：

```bash
export NV_ENDPOINT_NAME='query_items'
```

设置规则文件：

```bash
export NV_BODY_RULES=$PWD/validity/new_platform_rules.json
```

设置状态输出：

```bash
export NV_STATUS_PATH=/tmp/nv_http_status.json
export NV_BODY_VALID_STATS=/tmp/nv_body_valid_stats.json
```

---

## 13. 第五步：先做单次手工验证

在跑 AFL 前，必须先做一次单次请求验证。

```bash
cd ~/AFLplusplus

export NV_TARGET_CONFIG=$PWD/targets/new_platform.json
export NV_TOKEN='你的真实token'
export NV_ENDPOINT_NAME='query_items'
export NV_BODY_RULES=$PWD/validity/new_platform_rules.json
unset NV_BODY_SCORE_ENDPOINT
unset NV_BODY_SCORE_THRESHOLD
export NV_STATUS_PATH=/tmp/nv_http_status.json

python3 nv_http_harness.py < in/new_platform_body/seed_query_items_0.json || true
cat /tmp/nv_http_status.json
```

### 预期结果
理想情况下应看到：
- `http_code = 200`
- 或其他该平台正常业务响应码
- 不能是一上来就连接失败 / 鉴权失败

如果单次手工验证不通过，不要直接跑 AFL。

---

## 14. 第六步：验证一级规则是否生效

### 14.1 非法 JSON 验证

```bash
printf 'nnnnnn' | python3 nv_http_harness.py ; echo $?
```

预期：
- `reason = invalid_json`
- 返回码为 `0`（表示前置过滤成功，不计入平台 Err）

### 14.2 字段类型错误验证

```bash
cat > /tmp/bad_rule.json <<'EOF'
{"page":"not_int","size":10,"keyword":""}
EOF

python3 nv_http_harness.py < /tmp/bad_rule.json ; echo $?
```

预期：
- `reason = field_type_mismatch`
- 返回码为 `0`

---

## 15. 第七步：运行 baseline / rule_only

### 15.1 baseline
不启用 body 规则，只测试 body-only 请求执行。

### 15.2 rule_only
启用 `validity/new_platform_rules.json`，测试一级规则过滤。

如果你已经有通用化脚本，可以通过环境变量覆盖路径：

```bash
CFG=$PWD/targets/new_platform.json \
IN_DIR=$PWD/in/new_platform_body \
RULES_PATH=$PWD/validity/new_platform_rules.json \
DUR=120 \
./scripts/run_o2oa_main_baseline_rule.sh
```

如果当前脚本仍固定 O2OA 三个 endpoint，则建议先：
- 单接口手工跑
- 或后续把脚本抽象成“按 endpoint 列表运行”的通用版

---

## 16. 第八步：可选接入二级 score

如果新平台也要做二级 score 增强实验，建议先用现有 mock score 接口验证流程，再考虑接入真实模型。

### 16.1 启动 mock score

```bash
cd ~/AFLplusplus
pkill -f nv_valid_server_mock.py || true
rm -f /tmp/nv_valid.sock
export NV_RPC_FMT=text
export NV_VALID_SOCK=/tmp/nv_valid.sock
python3 nv_valid_server_mock.py
```

### 16.2 设置 score 环境变量

```bash
export NV_BODY_SCORE_ENDPOINT='unix:///tmp/nv_valid.sock'
export NV_BODY_SCORE_THRESHOLD='1.0'
```

### 16.3 运行带 score 的手工验证

```bash
python3 nv_http_harness.py < in/new_platform_body/seed_query_items_0.json ; echo $?
cat /tmp/nv_body_valid_stats.json
```

## 17. 第九步：判断迁移是否成功

如果下面这些条件都成立，则可认为“新平台最小接入成功”：

### target 层
- `targets/new_platform.json` 能正常加载
- endpoint 名称与规则文件一致
- body-only 模式能正常定位到目标接口

### validity 层
- 合法 seed 能通过
- 非法 JSON 能拦截
- 类型错误能拦截
- 主逻辑代码无需平台特判

### 执行层
- 单次手工请求能成功
- baseline 能跑
- rule_only 能跑
- 不出现大面积连接失败

### 可选 score 层
- score 服务能调用
- `body_score_rpc_ok > 0`
- `body_score_rpc_fail = 0`

## 18. 常见错误与排查方法

### 18.1 单次请求就失败
优先检查：
- `base` 是否正确
- token 是否正确
- `method` 和 `path` 是否正确
- 目标平台是否可访问

### 18.2 一直返回鉴权失败
检查：
- `auth.type`
- `header`
- `prefix`
- `token_env`
- 是否还需要 Cookie

### 18.3 规则一开就全 reject
检查：
- `required` 是否写错
- `allow_unknown` 是否过于严格
- `type` 是否与真实 body 结构不符

### 18.4 score 一直没效果
先确认：
- score 服务是否真的在运行
- `NV_BODY_SCORE_ENDPOINT` 是否正确
- `NV_BODY_SCORE_THRESHOLD` 是否合理
- 种子是否足够覆盖“规则通过但更异常”的区域

---

## 19. 迁移时不要做的事

### 不要做 1
不要一开始就改 `nv_http_harness.py` 主逻辑。

### 不要做 2
不要把平台特有规则写死进 `nv_body_valid.py`。

### 不要做 3
不要 target、rules、score、脚本一起改。

### 不要做 4
不要一开始就追求真模型，先把 target + rules + 手工验证做稳。

- [ ] 已创建 `targets/new_platform.json`
- [ ] 已创建 `validity/new_platform_rules.json`
- [ ] 已创建 `in/new_platform_body/`
- [ ] 已准备至少 1 个合法 seed
- [ ] 已设置 token / 鉴权环境变量
- [ ] 已完成单次手工请求验证
- [ ] 非法 JSON 能被拦截
- [ ] 类型错误能被拦截
- [ ] baseline 能运行
- [ ] rule_only 能运行
- [ ] 如需 score，score 服务可调用
- [ ] 输出结果可保存和复现

---

## 21. 建议的接入顺序总结

最推荐的顺序是：

1. 先写 `targets/new_platform.json`
2. 再写 `validity/new_platform_rules.json`
3. 再准备种子目录
4. 先做手工单次验证
5. 再验证一级规则
6. 再跑 baseline / rule_only
7. 最后才考虑 score 增强实验

这样最稳，也最容易定位问题。
