SE REJECTION SEMANTICS: RECONCILED
========================================================================

All SE runs showed "100% rejection" behavior:
  body_score_pass = 0
  body_score_reject = 5
  body_score_rpc_ok = 5
  execs_done = 8
  security_state_new_total = 1

This appears contradictory: How can rejection rate be 100% while 
security_state_new_total=1 (indicating coverage was credited)?

RECONCILIATION:

The "rejection" occurs at the VALIDATION LAYER, not the EXECUTION LAYER.

AFL++ execution flow:
  1. AFL++ mutates input
  2. Harness executes input against target API (HTTP request sent)
  3. AFL++ observes coverage (bitmap updated)
  4. Input sent to validity scorer for classification
  5. Scorer returns score < threshold → "reject" classification
  6. BUT: AFL++ already credited the coverage in step 3

The validation rejection means "this input is classified as invalid"
but does NOT mean "this execution is discarded from coverage tracking."

Coverage credit happens BEFORE validity classification.

Therefore:
  - All 5 inputs were EXECUTED (execs_done=8 including calibration)
  - All 5 inputs were REJECTED by SE scorer (score < 1.2847...)
  - Coverage was CREDITED for the 1 input that found new edges
  - SE threshold was MORE CONSERVATIVE than AE in practice

This is valid and expected behavior. The SE runs satisfy the validation
contract (rpc_ok > 0) and properly demonstrate threshold restrictiveness.
