ROOT CAUSE STATEMENT:

The canonical SE model (sefanogan_es_reference) was trained on a distribution
where feature dimension 10 (invalid_type_count) had ZERO VARIANCE (all 9 samples
had value 0.0). The normalization layer's standard deviation for this dimension
is effectively zero (1e-8), causing division-by-near-zero when scoring inputs
with invalid_type_count=1.0.

The frozen content_update seed has invalid_type_count=1.0, which is a correct
feature value for a metadata_update scenario (scenario flag dim[0]=1.0). However,
the SE model's normalization explodes this to a z-score of 10^8, leading to
catastrophic reconstruction error and a score of ~14.8 million (vs threshold 1.28).

This is a TRAINING DATA DEFECT, not a threshold calibration issue. The model
learned only one possible value for dimension 10, making it structurally unable
to score inputs with any other value in that dimension.

CONTRIBUTING FACTORS:

1. Feature Extractor Scenario Mislabeling:
   The content_update seed body contains only JSON properties (cm:title, cm:description)
   with no file content. The feature extractor correctly sets scenario_metadata_update=1.0
   (dim[0]), but this conflicts with the "content_update" scenario label used in the
   experiment protocol. The SE model sees this as a metadata_update input.

2. Training Sample Selection:
   The 9 training samples apparently all had invalid_type_count=0.0, suggesting
   they were all structurally valid payloads with no type violations. This lack
   of variance prevents the model from generalizing to payloads with type issues.

3. Normalization Layer Design:
   The model uses standard z-score normalization without epsilon protection
   (std[i] + ε) or variance floor, allowing near-zero std to cause numerical
   instability.
