C. Lifecycle

HTTP_HARNESS_LIFECYCLE = PER_EXECUTION_PROCESS
SEQUENCE_STORAGE       = <NV_STATUS_PATH>.seq   (one sidecar per status namespace)
CONCURRENCY_MODEL      = one execution at a time per namespace; separate
                         instances get separate namespaces (fuzz_gui.py);
                         allocation still done under flock(LOCK_EX)
RESTART_BEHAVIOR       = counter restarts at 1; C side treats a lower exec_seq
                         as a restarted counter and resynchronises

This was measured, not inferred. main() reads stdin once and exits — no __AFL_LOOP. The proof: the harness already had a module-level SEQ counter, and running it three times with identical input produced seq=1, seq=1, seq=1. That is precisely the forbidden pattern, already present in the shipping code. A process-lifetime counter cannot identify an execution when the process handles exactly one, so the counter had to outlive the process.

Allocation is open → flock(LOCK_EX) → read → +1 → truncate → write → fsync → unlock. If the sidecar cannot be maintained it returns 0, which the C side reads as "not reported" and handles via the legacy fallback — a degraded environment loses execution identity, not the observation.

REAL_HARNESS_REPLAY_UPGRADE = COMPLETE

Why COMPLETE rather than PARTIAL: the v0.7.0 boundary existed because one active writer — nv_http_harness.py — lacked execution identity. All three active NV status writers now emit exec_seq, and because every one of the ten HTTP launchers runs that single harness, no active real-HTTP path is left on the legacy fallback. I looked specifically for a writer that would force PARTIAL and did not find one; the candidates (nv_state_probe.py, the Alfresco wrappers, fuzz_gui.py) are not status writers, which I verified individually rather than by README.

The legacy fallback remains in the C code deliberately, for third-party or historical harnesses — that is compatibility, not an unupgraded writer.

What this does not mean. REAL_SERVICE_CROSS_PLATFORM_MIGRATION stays PARTIALLY_VERIFIED. Every execution here went to a local deterministic server on 127.0.0.1; no real O2OA, Alfresco or Flowable service was contacted, and no fuzzing campaign was run. Alfresco in particular is verified at the request-shape through the shared harness level, since the repo commits no Alfresco HTTP config.
