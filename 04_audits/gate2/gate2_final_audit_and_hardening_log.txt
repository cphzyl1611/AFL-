Fail-closed guard

The report's only value-bearing channel is a recorded path (finding path or skip path). Both channels were exercised, ASCII and Unicode, via subprocess:

2.finding-path.ascii    rc=1  stdout=0 bytes  report NOT created  SecretSerializationError  stderr clean
2.finding-path.unicode  rc=1  stdout=0 bytes  report NOT created  SecretSerializationError  stderr clean

2.skip-path.unicode     rc=1  stdout=0 bytes  report NOT created  SecretSerializationError  stderr clean
4.whitespace-padded secret still guarded                          PASS

Exception text is a fixed string and discloses nothing; the traceback carries no value. Unicode is handled correctly because ensure_ascii=False keeps non-ASCII secrets as their raw UTF-8 bytes, which the guard
compares against.

Finding — guard bypass on JSON-escapable characters

That same ensure_ascii=False design isrt_no_secrets compares the raw UTF-8bytes of the secret against the JSON-escaped serialization. When the secret contains a character JSON must escape, the two representations differ and the guard does not fire:

secret contains a double quote; loaded a scanned path

Reproduced for ", \, tab, and newline. In each case both sinks emitted, and the value is trivially recovered by JSON-decoding the report.

Scope and severity, stated fairly: the only way a runtime secret reaches the report at all is by being a substring of a scanned filesystem path, so real-world exploitability against this repository is
negligible, and the guard is defense-i guarantee that findings never carryvalues. But the claim under audit is specifically fail-closed, and the guard does not hold closed for the whole input space it accepts.
