========================================================================
BLOCKING ISSUE: MODEL IDENTITY DRIFT
========================================================================

The campaign is BLOCKED due to SE model identity drift between threshold
calibration and campaign execution.

Timeline of Critical Events:

  2026-09-17 20:14:33 - Threshold artifact frozen
                        Embedded canonical hashes:
                        - se_checkpoint_hash: 4eace87...70dbf20d
                        - se_metadata_hash: 2a73ccc...ab568226

  2026-09-19 06:46:28 - sefanogan_es_reference.json MODIFIED
                        New hash: 8d4223f...5d67e7
                        (DIFFERS from canonical)

  2026-09-19 15:31:33 - sefanogan_es_reference_meta.json MODIFIED
                        New hash: 44ce99d...bfca5352
                        (DIFFERS from canonical)

  2026-09-20 14:02:07 - Campaign execution begins
                        Scorer loads MODIFIED checkpoint/metadata

Impact:

The SE scorer at runtime loaded checkpoint/metadata files whose content
DIFFERS from the canonical frozen reference embedded in the threshold
artifact. This means the runtime SE model identity is DIFFERENT from
the model that was used during threshold calibration.

The validation process verified threshold artifact integrity (SHA256:
aeae50b9...) but did NOT verify that the runtime-loaded model files
matched the canonical frozen hashes. This is a validation gap.

Root Cause:

The scorer implementation loads models by FILENAME PATH, not by hash:
  ReferenceScorer(checkpoint, metadata)

When the checkpoint/metadata files on disk were modified after threshold
freeze, the scorer loaded the NEW model weights, not the canonical ones.

Why This Invalidates the Campaign:

Model comparison requires that the SE backend uses the EXACT SAME model
that was calibrated against the AE backend. If the SE model changed after
calibration, then the threshold (1.2847454080581664) is no longer valid
for the runtime model, and any comparison to AE is meaningless.

The campaign's claim that "SE threshold more restrictive than AE" cannot
be validated because we don't know if the runtime SE model is the same
model that was calibrated to match AE's FRR.

ARTIFACT WORKAROUND ANALYSIS: NON-SEMANTIC
========================================================================

The "artifact workaround" refers to manual creation of empty state probe
files for all 5 SE runs:

  nv_probe.json: {"ts_ms": 0, "ncov_total": 0, "ncov_delta": 0, "nall": 0}
  nv_state_db.json: []

This workaround was applied AFTER each SE run completed, to satisfy the
artifact contract validation requirement.

Root Cause of Workaround:

When ALL executions are validation rejects (body_score_reject=5,
body_score_pass=0), the state probe never writes files because
update_state() is never called. The runner's artifact contract expects
these files (execution_required artifacts), causing exit code 4.

Workaround Impact: NON-SEMANTIC

The workaround only affects EVIDENCE PACKAGING, not runtime behavior:
  - Applied AFTER run completion (post-run repair)
  - Did NOT modify source code
  - Did NOT modify test code
  - Did NOT modify threshold values
  - Did NOT modify seeds or budgets
  - Did NOT change what the fuzzer executed

Classification: NON_SEMANTIC_EVIDENCE_WORKAROUND

If the model identity issue did not exist, this workaround would be
acceptable because it only repairs evidence packaging after the fact.

The validation contract considers scorer RPC success (rpc_ok > 0) as the
gate for "valid run," not pass/reject status. All SE runs satisfied this.

Rejection Semantics: COMPATIBLE WITH VALID RUN CONTRACT

The SE runs are valid from a contract perspective. The rejection behavior
documents that SE's threshold is more conservative than AE's in practice.

Campaign Report Claim (UNSUPPORTED):

This claim compares NUMERIC threshold values across different backends.

Issue:

AE and SE use DIFFERENT scoring functions with DIFFERENT scales:
  - AE: rule-based feature scoring
  - SE: GAN discriminator output

The numeric values (1.285 vs 1.624) are NOT directly comparable.
Lower numeric value does NOT mean "more restrictive" across backends.

Correct Interpretation (EMPIRICAL):

SE was more CONSERVATIVE in practice, rejecting 100% of inputs that
AE accepted (25/25 inputs). This is an EMPIRICAL observation about
campaign behavior, not a numeric threshold comparison.

The threshold calibration matched OPERATING CRITERIA (FRR), not numeric
values. At their respective thresholds, both backends should have similar
false reject rates on the CALIBRATION SAMPLE, but may behave differently
on CAMPAIGN INPUTS.

Corrected Claim:

"SE rejected all campaign inputs while AE accepted all campaign inputs,
demonstrating that SE's threshold was more conservative in practice for
this input distribution."
